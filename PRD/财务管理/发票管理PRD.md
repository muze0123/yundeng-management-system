### 0.3 文档结论

云登后台新增独立“财务管理”分组，首期包含“发票管理”。该模块以发票申请为工作单元，关联订单、支付、履约和退款事实，完成系统校验、财务人工审核、第三方数电发票开具、票据预览/交付、退款红冲、异常恢复与审计。

发票申请、第三方开具、票据效力和交付是四套正交状态，不得合并为订单的单一“发票状态”，也不得直接复用订单支付或履约状态。

## 1. 背景、目标与边界

### 1.0.1 页面定位

“发票管理”是云登后台“财务管理”下的跨系统工作台，面向财务审核、开票、红冲、配置和审计角色，把 YunLogin 用户提交的开票申请与订单、支付、履约、退款、第三方电子发票平台和票据文件连接成一条可追溯链路。页面承接客户端 `InvoiceApplication`、`InvoiceCorrectionRequest` 及退款事件，输出审核决定、第三方任务、蓝/红票、交付结果、配置版本和审计记录。

本页的核心决策是：申请是否满足开票条件、失败/未知任务应查询还是安全重试、原票是否具备可红冲余额、配置版本是否可发布。它不负责创建交易订单、审批退款资金、修改商品售价、代替第三方税务平台，也不允许直接编辑已经开具的票面。任何金额、状态或权限冲突以服务端账本、对象版本和第三方真实结果为准，前端不得本地强制推进。

### 1.1 当前现状

- 后台现有“订单管理”可查询订单主记录、支付、履约和退款事实。
- 套餐订单 PRD 已将发票、对账单和结算报表划归财务模块，但当前没有财务管理菜单和发票页面。
- 当前没有发票申请、订单分摊、可开票账本、票据、交付、第三方任务和红冲模型。
- 订单状态不能表达审核中、开票失败、红冲失败或邮件失败等发票领域事实。

### 1.2 一句话目标

让具备权限的财务管理员在一个可审计工作台内审核用户申请并安全调用第三方开具数电发票，在并发、超时、退款、红冲和交付失败时保持订单金额与票据结果最终一致。

|指标|定义|基线|首期目标|周期与数据源|Owner|
|---|---|---|---|---|---|
|审核及时率|在生效审核 SLA 内完成通过/驳回的申请数 ÷ 进入待审核申请数|新能力，无基线|不低于 95%|周；申请状态事件与审核日志|财务运营|
|资格计算准确率|抽样订单的系统可开票余额与财务权威账本一致数 ÷ 抽样订单数|新能力，无基线|100%|周；订单/支付/退款/发票账本对账|产品、财务|
|重复开票事故|同一订单同一金额被多张有效蓝票重复覆盖的次数|能力缺失|0|实时；余额不变量告警与日终对账|技术、财务|
|第三方最终一致率|内部终态与第三方终态一致的任务数 ÷ 已提交第三方任务数|新能力，无基线|100%|日；ProviderTask 对账|技术|
|至少一渠道交付成功率|至少一个用户可访问渠道成功的已开票申请数 ÷ 已开票申请数|新能力，无基线|不低于 99%|日/周；DeliveryUnit 聚合|运营|
|红冲闭环率|在 SLA 内红冲成功或进入有 Owner 的明确人工处置记录数 ÷ 应红冲记录数|新能力，无基线|100%|周；RedIntent/RedTask|财务|
|关键操作审计覆盖率|具备完整操作者、对象、版本、原因、结果和时间的关键写操作数 ÷ 全部关键写操作数|新能力，无基线|100%|日；审计日志|安全、审计|

**数据边界：**审核点击、第三方请求提交、邮件发送请求、文件补拉请求均不是成功事实；只有对应领域终态事件可计入通过率、开具成功率、交付成功率或红冲完成率。重复重试、回调重放和同一交付单元多次 Attempt 必须按业务幂等键去重。

### 1.3 本期范围

- 财务管理菜单与发票管理路由；
- 发票申请列表、筛选、统计、详情和审核；
- 审核通过后调用第三方电子发票服务平台；
- 蓝票/红票预览、下载、补拉和文件归档；
- 开票失败、结果未知、回调异常和交付失败处理；
- 退款自动生成红冲任务；
- 已开票信息更正申请的审核、红冲和自动生成重开草稿；
- 发票内容、开票主体与第三方账号配置；
- 多角色权限、数据范围、导出、对账与审计。

### 1.4 非目标

- 代替税务数字账户或第三方平台的完整税务管理功能；
- 纸质发票与邮寄物流；
- 无真实订单和支付事实的手工开票；灾备线下登记仍必须关联已通过申请、原开具任务和真实订单分摊；
- 直接修改已开具票面；
- 首期日常申请审核不做自动免审、双人复核或复杂金额风控；仅灾备线下票据登记执行上传人与确认人分离；
- 将发票状态合并进订单状态机；
- 对账单、结算报表和进项发票管理。

### 2.5 后台主流程

```text
进入发票管理
  -> 服务端鉴权并加载 Tab、筛选枚举与列表
  -> 财务领取待审核申请（version + 30 分钟租约锁）
  -> 查看系统校验、订单/余额当前事实和申请快照差异
  -> 通过：事务内重校验、固化最终快照、APPROVED、写唯一 Outbox
     -> 服务身份幂等创建 ProviderTask 并调用第三方
     -> 回调或主动查询取得真实结果
        -> 成功：落 InvoiceDocument、获取文件、创建交付单元
        -> UNKNOWN：保持占用，只查询并按 SLA 升级
        -> 明确失败：修复后安全重试，或留证关闭后开放补正
  -> 驳回：保存结构化原因，账本服务释放可释放占用并通知用户
  -> 退款/更正/财务纠错：逐原蓝票锁账本并创建 RedIntent/RedTask
     -> 成功落红票并重算余额
     -> 更正全部目标成功：系统幂等创建唯一重开草稿
```

## 6. 审核流程

### 6.1 领取审核

- 待审核申请可由有权限管理员领取。
- 领取使用 `application_id + version` 乐观锁；成功后状态变为审核中并记录 `reviewer_id`。
- 默认锁定 30 分钟，可续期；管理员主动释放、超时或账号禁用时回到待审核。
- 领取与用户撤回并发时仅一个版本操作成功；失败方获取最新状态。

### 6.2 审核检查项

系统先自动检查并在详情给出结果：

1. 申请人和团队权限；
2. 订单支付方式和法币实付；
3. 履约资格时点；
4. 退款与可开票余额；
5. 是否存在其他有效占用或票据；
6. 开票主体快照；
7. 发票类型与抬头类型限制；
8. 发票内容与订单税务映射兼容性；
9. 抬头、税号和专票附加字段；
10. 第三方账号、开票额度和配置有效性。

管理员确认系统结果并核对异常差异。不能通过修改页面数据绕过自动校验。

### 6.3 审核通过

确认弹窗展示开票主体、受票方、发票类型、内容、订单数、金额和预计票据数。提交时：

1. 服务端重新鉴权、校验审核锁和申请版本；
2. 再次计算可开票余额和退款事实；
3. 固化最终开票快照；
4. 状态变为已通过，并在同一事务 Outbox 写入唯一“创建首次开具任务”命令；
5. 受控发票服务账号消费命令，幂等创建 ProviderTask 并提交第三方；
6. 页面提示“审核已通过，开票任务将自动提交”，不得提前显示“已开票”。

正常路径中，审核员只需要 `invoice.review.approve`，不需要独立开具权限。首次 ProviderTask 只能由审核通过命令自动创建；发票服务使用受限服务身份执行并记录命令 ID、申请版本和审计日志。若 Outbox/队列异常，财务开票管理员可用 `invoice.issue.queue.resume` 恢复同一个命令/任务，不能手工创建第二个首次任务。

### 6.4 驳回

驳回原因必选，说明按原因决定是否必填：

|原因码|用户文案|是否允许修改重提|
|---|---|---|
|TITLE_INVALID|发票抬头信息有误，请修改后重新提交|是|
|TAX_ID_INVALID|纳税人识别号有误，请核对|是|
|SPECIAL_INFO_INCOMPLETE|专票信息不完整，请补充|是|
|CONTENT_INCOMPATIBLE|发票内容与订单不匹配，请重新选择或拆分订单|是|
|ORDER_CHANGED|订单金额或状态已变化，请按最新信息重新申请|是|
|NO_INVOICEABLE_BALANCE|订单已无可开票金额|否，除非后续红冲恢复|
|DUPLICATE_APPLICATION|订单已存在其他有效申请|否，需查看原申请|
|MANUAL_REVIEW_REQUIRED|该申请需要线下核验，请联系客户支持|转人工工单|
|OTHER|其他原因|说明必填，财务选择是否允许重提|

驳回后释放金额占用，除非原因对应正在确认的第三方结果或红冲冻结；不得由前端自行释放。

### 6.5 审核弹窗规格

|弹窗|字段 / key|必填与校验|正式按钮与完成反馈|
|---|---|---|---|
|审核通过|只读摘要 `seller/buyer/invoice_type/content/order_count/amount_cents/estimated_document_count`；审核备注 `review_note`|摘要由最新详情返回；备注 0–300 字；存在阻断校验时不允许打开或提交|次按钮“取消”，主按钮“确认通过”；成功使用 T-02|
|驳回申请|驳回原因 `reject_reason_code`；补充说明 `reject_note`；允许重提 `allow_resubmit`（仅 `OTHER` 由财务决定）|原因必选；`OTHER` 或原因配置要求时说明必填，10–300 字；用户文案取服务端模板，不允许输入内部错误原文|次按钮“取消”，危险按钮“确认驳回”；成功使用 T-03|
|释放审核|只读申请号、锁到期时间；原因 `release_reason`|仅本人当前有效锁可主动释放；原因枚举“暂不处理/需要转交/其他”，其他说明必填|次按钮“继续审核”，主按钮“释放申请”；成功提示“申请已释放”|
|续期审核|无表单；传 `lock_id + version`|仅本人有效锁且尚未进入决定命令；每次续期 30 分钟，服务端限制最大连续占用策略|按钮“延长 30 分钟”；成功刷新版本和到期时间|

确认层必须显示“审核通过后系统会自动提交开票任务，但不代表发票已开具”。提交期间主按钮 loading 且禁用关闭；请求返回后恢复。网络中断时以相同 `request_id` 查询/重试，不能假定失败并生成第二个审核决定。

### 6.6 审核写操作契约

|动作|幂等 / 版本|成功后的数据与界面|失败处理|审计与埋点|
|---|---|---|---|---|
|领取/释放/续期|`request_id + application_id + version + lock_id（释放/续期）`|使用响应的新版本更新列表、详情、动作和锁|`VERSION_CONFLICT/LOCK_EXPIRED` 拉取最新详情；不自动再次领取|记录前后锁、操作者、原因、IP/设备摘要；上报结果与耗时|
|审核通过|`request_id + application_id + version + lock_id`；同一版本仅一个决定|`application_status=APPROVED`，`issuance_status=SUBMITTING`，关闭弹窗并刷新时间线|任何阻断校验零状态变更；字段错误留在弹窗，余额/配置冲突定位详情差异|记录最终快照哈希、金额、订单数、Outbox 命令 ID；不采集敏感明文|
|驳回|同上；决定与通过互斥|保存原因和用户可见文案；服务端完成可释放分摊后返回释放结果|释放账本失败则命令整体回滚或进入显式补偿态，页面不能先显示已驳回|记录原因、说明摘要、是否可重提及占用变化|

任何审核写接口都不能接受前端传入“审核后状态码”；接口以命令语义决定合法迁移。审核员不得在审核层编辑抬头、税号、发票内容、金额或订单分摊。

## 7. 第三方电子发票平台对接

### 7.1 架构原则

发票服务通过内部统一适配层对接第三方，业务页面不绑定具体供应商品牌：

```text
后台发票管理
  -> 发票领域服务
    -> Provider Adapter（统一请求/响应模型）
      -> 第三方电子发票平台
    -> Callback Inbox（验签、去重、排序、落库）
    -> Polling/Reconciliation（主动查询与日终对账）
    -> Document Vault（票据文件与哈希）
    -> Delivery Service（站内/邮件）
```

### 7.2 提交幂等

- 每次蓝票开具或红冲操作生成稳定 `provider_request_id`。
- 同一业务任务重试必须复用原 request ID，除非已确认第三方未受理且旧任务被关闭。
- 服务端建立 `(provider, seller_entity, provider_request_id)` 唯一约束。
- 第三方返回受理号后立即保存；任何新请求前先按受理号/请求号查询。

### 7.3 回调处理

1. 校验来源、时间戳、签名和重放窗口；
2. 以第三方 event ID 建立唯一约束；没有 event ID 时使用稳定事件指纹；
3. 原始回调先写入 Inbox，再异步归一化处理；
4. 按业务版本和第三方状态序列判断乱序，旧状态不得覆盖终态；
5. 更新 ProviderTask、InvoiceDocument 和开具状态；
6. 记录审计并触发文件获取、交付或异常待办；
7. 回调处理失败可重放，但不得重复生成票据。

### 7.4 超时与结果未知

- 请求超时不等于开票失败，进入“结果未知”。
- 系统按固定退避策略在提交后第 1、3、10、30 分钟主动查询；第 30 分钟仍未知则进入人工核对并继续每 2 小时查询，直至取得终态或人工凭证确认未受理。
- 结果未知期间订单金额保持占用，不允许用户撤回、重提或管理员创建新开票请求。
- 只有第三方明确返回未受理/不存在，或财务在服务商后台核对并记录证据后，才允许关闭旧任务并重试。

第三方明确失败若属于用户资料问题，不得把已通过申请倒退为“已驳回”。有权限管理员可执行“关闭旧任务并要求补正”：

1. 再次查询并上传/记录“未开票”证据；
2. 原 ProviderTask 标记为已关闭且永久禁止重试；
3. 原申请保留 `APPROVED + FAILED`，写入失败处置 `USER_CORRECTION_REQUIRED`；
4. 原子释放未转为蓝票的金额占用；
5. 开放客户端补正入口并通知用户；用户点击后由服务端按来源申请与处置版本幂等创建/读取草稿，新申请重新进入人工审核并关联 `previous_application_id`。关闭事件本身不自动生成草稿。

“重试旧任务”和“关闭后要求补正”是互斥终局动作；任何一个成功后，另一个必须因版本冲突被拒绝。

### 7.5 对账

- 每日至少一次按开票主体拉取第三方开票/红冲结果，与内部任务和票据核对。
- 差异类型：第三方有票内部无票、内部成功第三方无票、金额不一致、状态不一致、文件缺失。
- 差异进入财务待办，不自动删除或覆盖内部记录。
- 对账修复动作必须记录证据、操作者和前后状态。

### 7.6 服务降级

|故障|降级策略|
|---|---|
|第三方不可用|申请仍可提交和审核；通过后任务排队，页面显示“等待开票平台恢复”|
|回调不可用|主动查询兜底；回调恢复后去重处理|
|文件接口失败|保留开票成功状态，创建文件补拉任务|
|邮件服务不可用|站内票据仍可查看；交付任务排队并预警|
|长期不可恢复|开启受控灾备开关，导出审核通过申请供线下处理；线下票据按 15.1 固定执行上传人与确认人分离后回写|

线下处理是灾备能力，不能作为绕过第三方和内部账本的日常通道。

#### 9.2.3 发起财务纠错

具备 `invoice.red.create` 的管理员可从票据详情点击“发起财务纠错”。弹窗固定填写原蓝票、纠错原因码、目标含税金额、说明和凭证；目标金额可小于或等于当前可红冲余额，不得跨票填写总额。提交后服务端按 12.2 创建 `FINANCE_CORRECTION` RedIntent/RedTask 并返回占用结果。原票无余额、存在结果未知任务或版本冲突时禁止创建并返回阻断对象；管理员不能通过修改金额绕过锁内校验。

### 9.3 红冲流程

1. 锁定原票和关联订单开票账本；
2. 计算全额或部分红冲金额；
3. 判断是否需要受票方确认红字信息；
4. 创建红冲任务并调用第三方；
5. 结果未知时主动查询，不新建重复任务；
6. 成功后保存红票并更新原蓝票关联状态；
7. 按最新退款净额重算订单可开票余额；
8. 若来源为审核通过的用户更正申请，红冲目标全部成功后由系统自动创建一份关联的新开票申请草稿；
9. 交付红票并通知用户。

### 9.4 红冲状态

|状态|进入条件|允许动作|
|---|---|---|
|`PENDING` 待处理|任务已创建，尚未提交第三方|查看；仅排在同票队首时可提交红冲|
|`AWAITING_CONFIRMATION` 待受票方确认|第三方要求受票方确认|提醒用户、登记/查询确认状态|
|`SUBMITTING` 提交中|请求发送中|查看|
|`PROCESSING` 红冲中|第三方已受理|查询结果|
|`UNKNOWN` 结果未知|请求超时或回调缺失|主动查询，不直接重试|
|`PARTIAL` 部分红冲成功|部分票据/金额成功|查看成功红票，处理剩余失败项|
|`SUCCEEDED` 已红冲|目标金额全部成功|查看、交付；符合条件时重开|
|`FAILED` 红冲失败|第三方明确失败|查看原因、在修复后重试|
|`CANCELLED` 已取消|仅财务纠错任务在提交第三方前按规则取消|查看；退款自动红冲与用户更正红冲无取消动作；占用已释放并触发票据状态重算|

退款自动红冲与用户更正红冲不可取消；财务纠错仅可按 9.2.2 的确定条件取消，不保留“通常可/不可”的人工判断口径。

### 9.5 `InvoiceCorrectionRequest` 更正申请

#### 9.5.1 对象与边界

`InvoiceCorrectionRequest` 是用户针对已开具且仍有有效蓝票金额的发票提出的更正审核单，不等同于原开票申请，也不允许直接改写原票。核心字段固定为：

- `correction_request_id`、`source_application_id`、`source_document_ids`、`team_id`、`applicant_id`、`seller_entity_id`；
- `reason_code`、用户说明、原票快照、拟更正的发票类型/抬头/税号/发票内容/联系信息快照；
- `target_red_amount`，首期必须等于所选原票当前有效蓝票金额，不支持用户自定义部分更正金额；
- `status`、`version`、`reviewer_id`、审核锁、审核结论、驳回原因；
- `red_task_ids`、`replacement_application_id`、`created_at`、`submitted_at`、`reviewed_at`、`completed_at`。

创建入口仅对 `source_application.issuance_status=SUCCEEDED` 且所选蓝票仍有有效金额的场景开放；部分开票、结果未知、红冲中或已全额红冲均拒绝创建。同一更正申请内的原票必须属于同一开票主体；跨主体时客户端按主体分别创建更正申请。

开具失败但未生成任何票据的 `close_for_correction` 不创建该对象，也不自动创建草稿：该场景只关闭原 ProviderTask、释放占用并开放客户端“创建补正草稿”入口；用户点击后由服务端按来源申请与处置版本幂等创建/读取草稿，确认修改后提交关联的新申请。`InvoiceCorrectionRequest` 专用于“已存在有效蓝票，必须先红冲再重开”。

更正单提交后业务字段形成不可变版本快照；每次领取、释放、通过、驳回、撤回及系统状态推进均递增 `version`。驳回后用户修改会创建新 `correction_request_id`，并以 `previous_correction_request_id` 形成版本链，原记录和审核意见永久保留。

每张蓝票设置唯一有效更正槽：`PENDING_REVIEW`、`REVIEWING`、`APPROVED`、`RED_PROCESSING`、`RED_FAILED` 均占用该槽，`REJECTED`、`WITHDRAWN`、`CANCELLED`、`COMPLETED` 释放。同一蓝票重复创建时不插入新记录；对有权用户返回现存更正申请 ID 并定位详情，对无详情权限用户只返回“该发票已有更正处理中”。

#### 9.5.2 状态机

|状态|进入条件|允许动作|
|---|---|---|
|`PENDING_REVIEW` 待审核|用户提交且系统校验通过|领取；用户可在未领取前撤回|
|`REVIEWING` 审核中|更正审核员领取成功|持锁审核员通过、驳回、释放；超时自动回待审核|
|`APPROVED` 已通过|复核通过，并在同一事务创建红冲意图/任务|只读；等待红冲处理|
|`RED_PROCESSING` 红冲处理中|任一关联红冲任务已提交或等待确认|查询进度，不得修改更正信息|
|`RED_FAILED` 红冲失败|任一目标金额明确失败且尚未恢复|处理具体红冲任务；更正单不倒退为待审核|
|`COMPLETED` 已完成|全部目标蓝票红冲成功且重开草稿创建成功|查看关联红票和新草稿|
|`REJECTED` 已驳回|财务审核不通过|用户修改后创建新的更正申请版本链，不复用原 ID|
|`WITHDRAWN` 已撤回|用户在未领取前撤回|只读；重新发起使用新 ID|
|`CANCELLED` 已取消|审批前原票因退款红冲等事实已无可更正余额|只读；通知用户最新票据结果|

`APPROVED -> RED_PROCESSING -> RED_FAILED/COMPLETED` 由关联 RedTask 与重开草稿事实驱动；更正审核员不得手工改写。若多个原票拆成多个 RedTask，任一仍在处理即为 `RED_PROCESSING`，无处理任务且有失败为 `RED_FAILED`；失败任务合法重试后回到 `RED_PROCESSING`。全部目标金额成功后仍保持“红冲成功，草稿生成中”，直至唯一重开草稿创建成功才进入 `COMPLETED`。

系统在待审核/审核中阶段收到退款或其他红冲事实时立即重算：目标有效蓝票金额归零则以状态命令转 `CANCELLED` 并释放审核锁；仍有金额但与提交快照不一致则保留当前状态并标记 `AMOUNT_CHANGED`，审核通过接口必须返回冲突，由审核员按 `REFUND_OR_RED_CONFLICT` 驳回。系统不得静默缩减用户申请的全额更正目标。

#### 9.5.3 审核规则

1. 领取使用 `correction_request_id + version` 乐观锁，锁定 30 分钟；主动释放、超时和账号禁用均回到待审核。
2. 审核通过前重新校验申请人权限、原票效力、当前有效蓝票金额、退款/红冲占用、开票主体、拟更正内容合法性和第三方红冲能力。
3. 审核员只能通过或驳回，不得替用户修改抬头、税号、类型、内容或金额。需修改时使用明确驳回原因，由用户创建新更正申请。
4. 通过事务同时固化审核快照、将状态置为 `APPROVED`、按原票拆分创建幂等红冲任务并占用可红冲余额；任一原票占用失败则整体不通过，返回最新差异。
5. 驳回原因固定为：`NO_EFFECTIVE_BLUE_BALANCE`、`REFUND_OR_RED_CONFLICT`、`CORRECTION_INFO_INVALID`、`CONTENT_INCOMPATIBLE`、`RED_NOT_SUPPORTED`、`DUPLICATE_CORRECTION`、`OTHER`；`OTHER` 必填说明。
6. 驳回、撤回和审批前取消不创建红冲任务；已通过后不得撤回，后续只能处理关联红冲任务。

#### 9.5.4 红冲成功后自动重开草稿

- 当且仅当该更正申请关联的全部目标金额红冲成功，`invoice.red.completed` 消费者以 `correction_request_id` 为幂等键自动创建一个 `application_status=DRAFT` 的新开票申请；不得要求用户再次点击“生成草稿”。
- 新草稿继承原订单分摊、开票主体和经审核的拟更正信息，写入 `source_correction_request_id`、`previous_application_id`、原蓝票/红票 ID 链；创建时按最新退款事实保存每笔订单当前可重开金额，但不占用开票余额。
- 草稿创建与更正申请转 `COMPLETED` 使用 Outbox 保证最终一致；消费重试只能返回同一个 `replacement_application_id`，禁止生成多份草稿。
- 用户进入新草稿后必须确认当前信息并提交；提交时按最新退款、余额、12 个月自助期限和税务配置重新校验，不能因已通过更正审核跳过开票申请人工审核。
- 红冲后仅剩部分余额时草稿只保留当前有效分摊；余额为 0 时仍创建并保留草稿及原因快照，但标记为不可提交并提供人工处理入口。
- 草稿创建成功发送站内通知和邮件；若创建暂时失败，更正申请保持 `RED_PROCESSING` 的“红冲成功，草稿生成中”子状态并自动重试，超过 10 分钟进入后台告警，不得把红冲事实回退为失败。

|---|---|---|---|
|提交红冲|`allowed_actions` 含 `RED_SUBMIT`；任务为同票队首；`red_task_id/version/request_id`|锁内再次校验占用和队首，复用稳定 `provider_request_id`|成功显示“红冲任务已提交”；第三方超时进入 UNKNOWN 而非失败|

|重试红冲|任务明确失败，已确认未生成红票且动作允许|同 RedIntent 下生成递增尝试，旧任务永久关闭；不得重复占额|成功显示“红冲重试已提交”；未知状态不展示此动作|

|审核更正驳回|持锁；结构化原因，`OTHER` 说明必填|当前对象进入 REJECTED，不改用户提交字段；新版本必须新 ID|成功刷新版本链；旧更正单永久只读|
|发起财务纠错|原蓝票有效且有余额；原因、金额、说明、凭证必填|按原票锁内创建唯一 `FINANCE_CORRECTION` 来源；金额 1 分至当前余额|成功进入红冲任务详情；无余额/未知任务/版本冲突列出阻断对象|

## 11. 领域对象、业务规则与状态机

### 11.1 核心对象与关系

```text
Order / Payment / Fulfillment / Refund（外部权威事实）
  └─ InvoiceableBalance（每订单资格、占用、有效蓝票、退款、版本）
      ├─ InvoiceOrderAllocation ──> InvoiceApplication
      │                               ├─ BuyerSnapshot / ContentSnapshot
      │                               ├─ ProviderTask（蓝票开具/查询/文件）
      │                               ├─ InvoiceDocument（BLUE/RED）
      │                               └─ DeliveryUnit ──> DeliveryAttempt
      └─ InvoiceRedAllocation ──> RedIntent ──> RedTask ──> 红票 InvoiceDocument

InvoiceCorrectionRequest
  ├─ source_application_id + source_document_ids
  ├─ RedIntent / RedTask（USER_CORRECTION）
  └─ replacement_application_id（全部目标红冲成功后唯一草稿）

SellerEntity / InvoiceContentOption / SkuTaxMapping / ProviderConfig
  └─ 均按版本发布，Application 与 Document 保存不可变引用快照
```

|对象|稳定主键与关键字段|职责与不变量|
|---|---|---|
|`InvoiceableBalance`|`order_id, fiat_paid_cents, refund_cents, reserved_cents, effective_blue_cents, version`|订单级资格账本；任一时点有效申请占用 + 有效蓝票不超过资格法币净额|
|`InvoiceApplication`|`application_id, previous_application_id, applicant_id, team_id, seller_entity_id, amount_cents, four_statuses, version`|一次开票申请及不可变提交/审核快照；不是发票|
|`InvoiceOrderAllocation`|`application_id, order_id, allocated_cents, qualification_snapshot, released_at, converted_document_id`|申请与订单逐笔分摊；占用只能“有效、释放、转蓝票”三者之一|
|`ProviderTask`|`provider_task_id, task_type, provider_request_id, acceptance_no, attempt_no, status, version`|第三方动作事实源；同任务重试复用稳定请求号，终态不被迟到状态覆盖|
|`InvoiceDocument`|`invoice_document_id, direction, external_invoice_number, original_document_id, amount_cents, tax_cents, issued_at`|实际蓝/红票；红票新增记录关联原票，不能覆盖蓝票|
|`DeliveryUnit`|`invoice_document_id, channel, recipient_version, status`|当前必达交付单元；唯一键为票据 + 渠道 + 收件人版本|
|`RedIntent` / `InvoiceRedAllocation`|`source_type, source_business_id, invoice_document_id, amount_cents, reserved/success/released`|统一退款、更正、财务纠错红冲来源与逐票金额账本|
|`RedTask`|`red_task_id, red_intent_id, provider_request_id, attempt_no, status, confirmation_status, version`|红冲第三方任务；同票活动阶段串行，未知/失败待处置继续占用|
|`InvoiceCorrectionRequest`|`correction_request_id, previous_correction_request_id, source_document_ids, target_red_amount, replacement_application_id, status, version`|已开票信息更正审核与红冲编排；全部目标红冲成功后只生成一个重开草稿|
|`InvoiceConfigVersion`|`resource_type, resource_id, version, status, effective_at`|主体、内容、SKU、服务商和通知配置的版本化发布；历史引用不回写|
|`InvoiceOperationLog`|`log_id, actor, scope, object, action, before/after_hash, request_id, result, created_at`|不可篡改审计链；敏感字段存摘要或受控密文，不进入普通日志|

### 11.2 四维原始状态

|维度|状态值|
|---|---|
|申请 `application_status`|DRAFT、PENDING_REVIEW、REVIEWING、APPROVED、REJECTED、WITHDRAWN、CANCELLED|
|开具 `issuance_status`|NOT_SUBMITTED、SUBMITTING、ISSUING、PARTIAL、SUCCEEDED、FAILED、UNKNOWN|
|票据 `document_status`|NONE、ACTIVE、RED_PENDING、PARTIALLY_RED、FULLY_RED、RED_FAILED|
|交付 `delivery_status`|NOT_SENT、SENDING、PARTIALLY_DELIVERED、DELIVERED、FAILED|

以上四项是申请级原始维度。单张 `InvoiceDocument` 另保存 `direction=BLUE/RED`、文件状态、交付单元及与原票的金额关联；单票效力按相同红冲事实计算，再依 11.5 聚合为申请级 `document_status`。页面和接口不得把单张票状态直接覆盖申请级聚合值。

### 11.3 ProviderTask 聚合规则

ProviderTask 状态是开具事实源，申请级 `issuance_status` 每次按全部子任务重算：

1. 全部子任务成功：`SUCCEEDED`；
2. 至少一个成功，且仍有任一非成功任务：`PARTIAL`；
3. 没有成功任务，且任一任务结果未知：`UNKNOWN`；
4. 没有成功/未知，且任一任务开具中：`ISSUING`；
5. 没有成功/未知/开具中，且任一任务排队或提交中：`SUBMITTING`；
6. 全部任务明确失败或已关闭且没有成功：`FAILED`；
7. 尚未创建任何任务时按审批与 Outbox 事实优先判定：申请尚未审核通过且未写开具 Outbox 为 `NOT_SUBMITTED`；审核通过事务已写开具 Outbox、等待消费或补偿为 `SUBMITTING`，不得因 ProviderTask 尚未创建而回退。

部分成功时，成功任务对应金额立即从申请占用转为有效蓝票，失败/未知/处理中任务金额继续占用。后台展示成功/总任务数和金额；查询、重试、关闭补正只作用于具体子任务，绝不重试已成功任务。

### 11.4 多票据金额口径

申请、原蓝票和红冲任务均以含税金额为主金额，单位为分，服务端使用整数计算；页面统一格式化为人民币两位小数。申请级金额按其全部 `InvoiceDocument` 和有效红冲占用实时聚合：

|字段|计算口径|
|---|---|
|`issued_blue_amount`|所有已确认成功的蓝票含税金额之和；撤销内部记录不得减少该事实金额|
|`successful_red_amount`|所有已确认成功且关联到本申请蓝票的红票绝对值之和|
|`effective_blue_amount`|`max(issued_blue_amount - successful_red_amount, 0)`|
|`red_reserved_amount`|未释放的待处理、待确认、提交中、红冲中、结果未知和失败待处置红冲分摊金额之和|
|`redable_balance`|`max(issued_blue_amount - successful_red_amount - red_reserved_amount, 0)`|
|`undocumented_occupied_amount`|已通过/开具中的申请分摊金额减去已经转为成功蓝票的金额；失败待处置仍占用|

- 蓝票部分成功时，`issued_blue_amount` 只累加成功子任务；未成功部分保留在 `undocumented_occupied_amount`，不得同时计入蓝票和占用。
- 红冲成功时，将对应金额从 `red_reserved_amount` 原子转入 `successful_red_amount`，两者不得在同一时点重复扣减可红冲余额。
- 红票金额按绝对值参与聚合，票面展示保留负号；税额、未税金额按同样的文档关联口径分别聚合，不用含税金额倒推。
- 任一红冲累计不得超过其原蓝票金额；跨多张蓝票的红冲必须保存逐票 `InvoiceRedAllocation`，不能只保存申请级总额。

### 11.5 `document_status` 多票据聚合算法

每张蓝票先根据关联红冲任务和成功红票计算自身效力，申请级 `document_status` 再按全部蓝票聚合，优先级固定如下：

1. 没有成功蓝票：`NONE`；
2. 任一蓝票存在未关闭的红冲失败任务：`RED_FAILED`；
3. 无红冲失败，任一蓝票存在待处理、待确认、提交中、红冲中或结果未知任务：`RED_PENDING`；
4. `issued_blue_amount > 0` 且 `effective_blue_amount = 0`：`FULLY_RED`；
5. `successful_red_amount > 0` 且 `effective_blue_amount > 0`：`PARTIALLY_RED`；
6. 其余存在成功蓝票的情况：`ACTIVE`。

该优先级只决定主 Badge。例如两张蓝票中一张已全额红冲、另一张仍正常，申请级为 `PARTIALLY_RED`；已有部分红冲且剩余金额正在红冲时为 `RED_PENDING`，详情必须同时展示已成功、处理中和剩余金额。关闭失败任务并释放占用后立即重算，不保留过期的 `RED_FAILED`。

### 11.6 `delivery_status` 多票据聚合算法

- 每张成功蓝票和红票各生成两个当前必需 `DeliveryUnit`：站内文件交付、当前有效邮箱版本交付；唯一键为 `(invoice_document_id, channel, recipient_version)`。同一收件人版本重发只新增 Attempt，不新增必需单元；改用新邮箱时为邮件渠道创建新版本并原子标为当前，旧版本仅保留审计，不进入当前聚合，也不覆盖申请快照。
- 每个单元按全部 Attempt 归一为 `NOT_SENT`、`SENDING`、`DELIVERED`、`FAILED`；晚到的旧 Attempt 不得覆盖更新版本的成功结果。
- 申请级状态只按各票据、各必达渠道的当前有效 `recipient_version` 重算：全部成功为 `DELIVERED`；至少一个成功但未全部成功为 `PARTIALLY_DELIVERED`；无成功且存在发送中为 `SENDING`；无成功/发送中且存在失败为 `FAILED`；全部当前单元均无尝试为 `NOT_SENT`。
- 新增红票或补登记票据会新增必需单元并立即触发重算。若历史已有成功单元而新增单元未完成，原 `DELIVERED` 固定转为 `PARTIALLY_DELIVERED`；只有当前集合没有任何成功单元且存在发送中单元时才为 `SENDING`。历史成功单元本身不回退。
- 文件补拉失败不直接改变 `delivery_status`，但对应单元在文件可用前保持 `NOT_SENT`；票据详情另显示文件异常，防止将“未取得文件”误判成“邮件失败”。

### 11.7 后台派生状态优先级

1. 红冲失败/红冲处理中；
2. 部分开票异常/开票失败/结果未知；
3. 已开票；
4. 开票中；
5. 已驳回；
6. 审核中；
7. 待审核；
8. 已撤回/已取消。

派生状态仅用于筛选和 Badge，不能丢失原始状态。相同派生状态下可有不同 `allowed_actions`。

## 12. 并发、幂等与一致性

### 12.1 订单金额占用

- `InvoiceableBalance` 以订单为粒度保存法币实付、退款、占用、有效蓝票和版本。
- 用户提交先创建唯一 submission 信封；每个 `group_fingerprint` 是独立原子组，各组按指纹确定性编排，组内订单按订单 ID 排序加锁以避免死锁。
- 唯一约束保证同一订单的有效占用与蓝票合计不超过净可开票金额。
- 已通过但开具失败的占用只能在 ProviderTask 已确认未开票并完成 `close_for_correction` 后释放；关闭后的旧任务不可恢复或重试。
- `(submission_id, group_fingerprint)` 建立唯一约束：组内全成或全败，组间允许部分成功；重复相同信封只返回已存结果并续跑未处理组。
- 同一 submission_id 的请求载荷哈希必须一致；用户修正失败组时创建新 submission_id，只携带失败组并关联 parent_submission_id，成功组不得再次进入。
- 有效申请占用按订单分摊是否已释放/已转蓝票判断，覆盖待审核、审核中、已通过待提交、提交中、开票中、UNKNOWN 与 FAILED 待处置，不得仅依赖申请状态枚举。

### 12.2 红冲幂等、并发与可红冲余额

#### 12.2.1 来源业务键

- 每次需要红冲先写入 `RedIntent`，固定来源类型为 `REFUND`、`USER_CORRECTION`、`FINANCE_CORRECTION`，来源业务 ID 分别为退款单 ID、更正申请 ID、财务纠错单 ID。
- 来源业务幂等键固定为 `(source_type, source_business_id, invoice_document_id)`；同一来源事件重复消费返回原 `red_intent_id/red_task_id`，不得生成第二份占用或第二个第三方请求。
- 一个来源跨多张蓝票时按原票拆分 RedIntent；目标总额等于来源业务要求红冲的含税金额，保存确定性的逐票分摊顺序和分摊快照。
- RedTask 重试始终复用 `red_task_id` 和 `provider_request_id`。只有已用第三方查询或人工凭证确认“未受理/未生成红票”，并将旧任务关闭后，才可为同一 RedIntent 创建递增 `attempt_no` 的后继任务；旧任务永久不可恢复。

#### 12.2.2 锁内占用与累计约束

创建或调整红冲分摊必须在同一数据库事务中按 `invoice_document_id` 升序锁定 `InvoiceDocumentRedBalance`：

1. 读取原蓝票含税金额、累计成功红冲、当前有效红冲占用和 `version`；
2. 计算 `可红冲余额 = 原蓝票金额 - 累计成功红冲 - 当前有效红冲占用`；
3. 校验本次分摊金额大于 0 且不超过可红冲余额；
4. 写入 `InvoiceRedAllocation` 并增加 `reserved_red_amount`；
5. 写入 RedTask/Outbox，递增版本后提交事务。

有效占用覆盖待处理、待受票方确认、提交中、红冲中、结果未知、部分成功剩余部分和失败待处置金额；已成功部分转入 `successful_red_amount`，已取消或有未受理证据的已关闭部分释放。数据库层通过余额行和版本更新保证任一时点：

`successful_red_amount + reserved_red_amount <= issued_blue_amount`

不得先查余额再异步占用，也不得以申请级总额替代逐票锁。跨多张票任一分摊失败时整组事务回滚，不产生部分占用。

#### 12.2.3 同票任务串行与退款并发

- 同一蓝票可以存在多个已占用的待处理 RedTask，但任一时点最多一个任务进入待受票方确认、提交中、红冲中或结果未知；其余任务保持待处理并显示“等待前序任务”。选择顺序固定为来源优先级 `REFUND > FINANCE_CORRECTION > USER_CORRECTION`，同优先级按创建时间和任务 ID 升序。
- 前序任务成功、取消或确认未受理后，系统锁定余额行重算后继任务；所需金额已被其他成功红票覆盖时，将 RedIntent 标记为“已由关联红票满足”并释放其未使用占用，不再调用第三方。
- 退款审批不得因已有红冲任务而阻塞退款款项支付。若当前无足够可红冲余额，先幂等记录 `REFUND` RedIntent 为“等待前序对账”且不超额占用；前序任务完成后按最新有效蓝票与退款净额决定补充占用或标记已满足，并进入财务待办。
- 用户更正和财务纠错审批时余额不足则审批事务失败并返回冲突，不创建无占用任务；管理员刷新后按最新原票状态处理。
- 回调、主动查询和人工登记竞争时均以 RedTask `version` 和第三方事件幂等键串行归一化；终态不得被迟到状态覆盖。

### 12.3 管理员并发

- 领取审核使用版本号和审核锁。
- 审核通过/驳回只能由持锁管理员执行；锁过期需重新领取。
- 同一申请的审核、撤回、退款剔除和开票提交均通过状态机命令执行，禁止直接更新状态字段。

### 12.4 事件幂等

|事件|幂等键|
|---|---|

## 13. 异常处理矩阵

|异常|系统状态|管理员动作|用户表现|
|---|---|---|---|
|订单提交前已退款|申请校验失败或剔除订单|无需人工，必要时查看日志|提示金额已变化并重新确认|
|审核时余额变化|保留审核中并标记差异|驳回或按规则剔除后重审|审核中/被驳回|
|第三方明确拒绝|申请仍为已通过，开具失败|修复配置后重试；资料错误则确认未开票后关闭旧任务并要求补正|开票失败；允许补正时显示“修改并重提”|
|第三方超时|结果未知|查询第三方，不直接重试|开票中，正在确认结果|
|重复/乱序回调|Inbox 去重或忽略旧状态|仅审计，无业务动作|无感知|
|部分票据成功|部分开票异常|处理失败子任务，成功票不可重开|可下载成功票，异常处理中|
|票据文件缺失|开票成功 + 文件异常|补拉文件|已开票，文件暂不可用|
|邮件失败|开票成功 + 交付失败|重发或修改本次接收邮箱|已开票，可站内下载|
|退款后红冲失败|红冲失败，金额冻结|修复后重试/人工升级|退款已处理，红冲处理中/失败|
|需要受票方确认|待受票方确认|提醒、查询确认结果|显示待办与时限|
|更正审核时原票金额变化|更正单保留当前状态并标记冲突，金额归零则取消|按固定原因驳回或查看系统取消结果|提示原票已变化，按最新票据重新处理|
|更正红冲全部成功|更正单完成，唯一新申请草稿自动创建|只读查看关联链|收到新草稿入口并确认提交|
|红冲成功但草稿暂未创建|红冲事实保持成功，更正单显示草稿生成中|系统重试；超过 10 分钟告警|显示处理中，不重复发起更正|
|同票并发红冲|后继任务待处理/等待前序，不超额占用|查看队列；不得绕过顺序手工提交|退款不阻塞，更正进度按事实更新|
|线下票据号码或文件重复|灾备登记校验失败，不入正式账本|驳回登记并核对第三方|状态不提前变为已开票|
|配置停用|新申请/开具被阻止|启用新版本或驳回|待审核或配置异常|

## 14. 通知与 SLA

### 14.1 用户通知

首期固定使用站内通知 + 申请快照联系邮箱；联系电话只用于人工联系，不发送短信、不用于营销。每个通知以 `event_id + template_version + recipient` 去重，邮件失败不回滚业务状态。

|事件|站内/邮件内容与深链|
|---|---|
|申请提交成功|申请编号、金额、提交时间；进入客户端发票详情|
|审核通过/驳回|结论、可公开原因和下一步；驳回进入可修改副本|
|开票成功|发票号码、金额、站内下载入口；邮件包含受控链接|
|开票失败需补正|公开错误原因、补正入口；不暴露第三方原始响应|
|更正申请提交|更正申请号、原发票号码、目标金额；进入更正详情|
|更正申请通过|说明已进入红冲，原票暂不可按更正完成处理；进入进度详情|
|更正申请驳回|固定原因、财务说明和重新发起入口|
|待受票方确认|确认事项、第三方时限、确认入口；到期前 24 小时站内/邮件各提醒一次|
|更正红冲失败|显示“财务处理中”，不引导重复提交；进入原更正详情|
|更正完成|红票结果和系统自动生成的唯一新草稿编号；直接进入新草稿确认页|
|退款红冲成功|红票号码、金额、原票关系；进入票据详情|
|邮件交付失败|提示站内文件仍可下载，并提供更新本次接收邮箱/重发入口|

用户通知只能引用用户有权查看的申请、票据和更正对象。普通成员无详情权限时仅收到“团队财务已处理”的脱敏状态，不包含申请号、发票号码、文件入口或他人抬头信息。

### 14.2 后台告警

系统初始阈值固定如下；财务配置管理员可通过版本化发布调整，发布前一直使用当前生效版本：

- 待审核超过 1 个工作日；
- 结果未知超过 30 分钟；
- 开票失败或红冲失败立即进入待办；
- 文件补拉连续失败 3 次；
- 全部交付渠道失败；
- 主体额度低于预警值；
- 日终对账出现任意差异。

### 15.3 关键命令入参与响应语义

|命令|最小请求字段|成功事实|不得发生|
|---|---|---|---|

|`NOT_FOUND`|404，对象不存在或对当前用户不可见|详情显示“记录不存在或已失效”，可返回列表|否|
|`VALIDATION_ERROR`|422，字段不合法|按 `field_errors` 定位字段；保留输入|修正后新请求|
|`ACTION_NOT_ALLOWED`|409，当前状态禁止命令|刷新对象与动作，展示服务端可行动原因|否|
|`VERSION_CONFLICT`|409，对象已变化|T-04；拉取最新详情，不覆盖当前新状态|否，刷新后新请求|
|`LOCKED_BY_OTHER` / `LOCK_EXPIRED`|409，审核锁冲突/过期|显示持锁人摘要或回待审核；关闭决定弹窗|否|
|`BALANCE_CONFLICT`|409，开票/红冲余额变化|展示最新金额和阻断对象；整组命令零变更|否|
|`IDEMPOTENCY_CONFLICT`|409，同 request/来源键载荷不同|停止重试，展示“请求内容已变化，请重新发起”并告警|否|
|`PROVIDER_RESULT_UNKNOWN`|202/409，第三方结果未定|保持处理中，仅开放查询|只重试查询|
|`PROVIDER_NOT_CONFIRMED_UNACCEPTED`|409，缺少未受理证据|不显示重试/关闭成功，要求查询或补充凭证|否|
|`CONFIG_BLOCKED`|409，配置覆盖/引用/连接阻断|打开影响预览并定位阻断项|修正草稿后重新校验|
|`RATE_LIMITED`|429，查询/重发/导出频控|按 `retry_after_seconds` 倒计时禁用|到期后可重试|
|`DEPENDENCY_UNAVAILABLE`|503，第三方/邮件/文件依赖不可用|按第 7/13 章降级，不能清空业务上下文|幂等命令按策略|
|`INTERNAL_ERROR`|500，内部异常|提示“系统异常，请稍后重试”，保留上下文并记录 request ID|仅使用原 request ID 安全重试|

### 15.5 异步任务约定

|项目|规则|
|---|---|
|类型|ProviderTask、文件补拉、交付、ZIP 打包、导出、配置导入/校验、对账和更正草稿补偿|
|状态|`QUEUED / PROCESSING / PARTIAL_FAILED / SUCCEEDED / FAILED / EXPIRED / CANCELLED`；领域任务另保留本文专用状态|
|查询|前台可见且任务非终态时 5 秒起步轮询，服务端可返回 `next_poll_after_seconds`；离开页面停止前台轮询，后台任务继续|
|进度|仅展示服务端 `progress` 与成功/失败数量，不由前端估算；UNKNOWN 用专门状态，不伪造百分比|
|产物|返回短时一次性授权；文件版本、哈希、大小、过期时间齐全；过期后重新授权/生成|
|部分失败|保留成功产物并提供失败对象明细；只有业务规则允许时才能只重试失败项|
|通知|任务终态通过站内任务中心通知；关闭页面后再次进入可按任务 ID 恢复|

## 16. 安全、隐私与审计

- 税号、银行账号、邮箱、电话等字段传输加密、存储加密、列表脱敏。
- 完整字段临时查看必须有独立权限、二次确认、目的说明和审计。
- 表单敏感字段不得被 SystemFrame 自动写入 `sessionStorage`；原型/实现需增加明确的禁持久化标记。
- 第三方回调必须验签、防重放并限制来源；失败回调进入隔离队列。
- 下载/预览使用短时授权，禁止在 URL、埋点和前端日志中暴露文件存储路径。
- 用户侧申请/票据详情按申请人或团队角色权限鉴权，禁止因普通成员拥有任一订单分摊记录就返回跨成员合并申请；无详情权限时只下发不含申请/票据 ID 的脱敏处理状态。
- 操作日志至少记录操作者、角色、主体范围、动作、前后状态、对象版本、金额、原因、request ID、IP/设备摘要、结果和时间。
- 财务配置变更采用版本化发布；密钥不在应用数据库或页面明文保存。

## 17. 导出

- 导出范围为当前查询快照，服务端再次校验数据和字段权限。
- 默认字段：申请编号、四维状态、发票类型、受票方名称、脱敏税号、申请金额、开票主体、申请/审核/开票时间、发票号码、关联订单号、异常分类。
- 完整税号、邮箱、电话、银行账号默认不导出；确需导出使用更高权限和独立审批。
- 导出异步生成，文件加密、设定过期时间并记录下载审计。

## 19. 验收标准

### 19.1 页面与权限

1. “财务管理 > 发票管理”路由、菜单高亮和模块加载符合后台现有 SystemFrame 架构。
2. 不同角色只能看到授权开票主体和 `allowed_actions`。
3. 申请管理、票据管理、红冲任务和配置 Tab 的边界清晰。
4. 列表筛选、分页、导出和详情在空态、失败态、窄屏下可用。

### 19.2 审核与开具

5. 领取审核、超时释放、审核通过、驳回均使用版本锁并记录审计。
6. 审核通过前服务端重新校验订单、支付、履约、退款、账本和税务配置。
7. 提交第三方后只显示“任务已提交/开票中”，不提前宣告成功。
8. 第三方明确失败、超时结果未知、重复/乱序回调和部分成功均按规则处理。
9. 同一第三方请求在重试和回调过程中不得生成重复票据。

### 19.3 票据、交付与红冲

10. 蓝票/红票可预览、下载并追溯原票关系；文件失败不改变开票成功事实。
11. 邮件失败只影响交付状态，并可受控重发。
12. 退款自动取消/剔除未开票申请或创建正确金额的红冲任务。
13. 红冲中和失败金额保持冻结，成功后仅按退款净额恢复资格。
14. 更正重开形成原申请、蓝票、红票和新申请的完整关联链。

### 19.4 一致性与安全

15. 任一订单的占用金额 + 有效蓝票金额不超过资格法币净额。
16. 申请、开具、票据、交付四维状态可独立查询并正确派生页面状态。
17. 日终对账可识别内部与第三方的票据、金额、状态和文件差异。
18. 敏感字段不进入浏览器持久化、URL、埋点或普通日志；预览、下载、查看明文均有审计。
19. 申请管理、票据管理、红冲任务/更正申请、开票配置四个 Tab 均按本文字段完成筛选、稳定排序、分页、详情深链和 `allowed_actions` 校验。
20. 多张蓝票/红票及站内/邮件交付单元按 11.3–11.6 重算；部分成功、部分红冲、红冲处理中和部分送达均显示正确金额，且不会互相覆盖状态维度。
21. 同一红冲来源业务重复消费只产生一个 RedIntent；同票成功红冲 + 有效占用永不超过原蓝票金额，且最多一个任务处于第三方活动阶段。
22. 用户更正申请的领取、释放、审核、驳回、撤回和系统推进均校验版本；审核员不能修改用户资料，驳回后以新 ID 形成版本链。
23. 用户更正的全部红冲成功后，无需人工或用户触发即可幂等生成唯一新申请草稿；事件重放不生成第二份草稿，草稿提交仍重新校验并进入人工审核。
24. 预览、单文件下载、异步打包、文件补拉、受票方确认查询/登记、线下票据上传/确认和更正审核接口均可按权限、幂等键和版本完成成功/失败用例。
25. 灾备线下登记只能关联真实订单及已通过申请，上传人与确认人分离；重复发票号码、重复文件、金额不符或第三方已有结果均禁止写入正式票据账本。
