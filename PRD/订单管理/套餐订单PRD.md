## 1. 需求概述

### 1.0.1 页面定位

套餐订单是云登后台「订单管理」中的业务列表页，面向运营、客服、财务和系统管理员查询个人用户与企业的套餐购买、续费、支付、权益履约及退款结果。页面承接支付系统的订单事实、套餐版本快照和权益中心的履约结果，输出关闭待支付订单、补发或重试权益、发起或重试退款等受控动作。

核心决策是：订单是否真实支付、套餐权益是否已正确到账、异常是否需要人工恢复，以及订单是否满足退款条件。页面不负责配置套餐售价或权益模板，不允许直接编辑订单金额、支付流水、权益数量和有效期；这些能力分别由套餐配置、支付系统和权益中心承担。

> 关键原则：**支付成功不等于履约成功**。支付状态与履约状态必须独立展示、独立流转，禁止仅依据前端按钮点击或支付状态推断权益已到账。

### 1.1 背景与问题

套餐订单同时涉及支付事实、套餐版本快照和权益到账。若后台只展示单一「订单状态」，会把支付成功与权益到账混为一谈，导致履约失败难以及时发现、人工补发可能重复授予权益、退款后权益未回收等风险。

本需求建立统一的套餐订单查询和处置入口：将支付、履约、退款拆为可追溯状态；以套餐快照保护历史订单口径；通过权限、二次确认、幂等和审计约束人工操作。

### 1.2 一句话目标与成功指标

**一句话目标：**让授权后台人员在一个页面内识别个人与企业套餐订单的支付和履约差异，并安全完成关闭、补履约和退款恢复，使每一笔资金状态与权益变更均可追溯。

| 指标 | 定义 | 基线 | 目标 | 周期 | 数据来源 |
|---|---|---|---|---|---|
| 履约成功率 | 最终履约成功订单数 / 已支付订单数 | 待采集 | >= 99.9% | 日 / 周 | 订单服务、权益中心 |
| 履约及时率 | 支付成功后 60 秒内履约成功订单数 / 已支付订单数 | 待采集 | >= 99.5% | 日 | 履约任务日志 |
| 重复授予率 | 重复产生有效权益的订单数 / 已支付订单数 | 待采集 | 0 | 日 | 权益审计 |
| 退款权益一致率 | 退款成功且权益回收完成订单数 / 退款成功订单数 | 待采集 | 100% | 日 | 支付、权益对账 |
| 列表查询可用性 | 成功返回列表请求数 / 列表请求总数 | 待采集 | >= 99.9% | 月 | API 监控 |

**数据边界：**支付渠道未返回成功结果前不得记录为已支付；权益中心未确认写入前不得记录为已履约；前端展示状态不得替代服务端事实。

### 1.5 已确认事实与一期实现口径

**已确认事实：**

- 套餐购买主体支持个人用户和企业。
- 套餐主要权益信息包含权益项、环境数、成员席位和有效期。
- 后台支持订单操作，并需覆盖订单履约逻辑。
- 新页面需同步全局侧栏、系统框架路由和原型入口。

**为形成一期闭环采用的实现口径（待评审，不冒充线上既有事实）：**

| 类型 | 一期口径 | 若不成立的影响 |
|---|---|---|
| 退款 | 仅支持原路全额退款；退款金额只读且不得超过实付金额 | 若需部分退款，须补充优惠分摊、税费和剩余权益计算 |
| 权益回收 | 退款前校验可回收；退款成功后回收本订单授予的权益 | 若允许带权益退款，需定义欠费 / 负额度策略 |
| 个人席位 | 个人套餐成员席位显示为 1，不开放多人协作 | 若个人也支持多席位，套餐快照和展示规则需调整 |
| 生效时间 | 新购从履约成功时生效；续费按原到期日顺延，已过期则从履约成功时生效 | 若按支付时间生效，异常履约期间会消耗有效期 |
| 状态权威源 | 支付状态以支付服务为准，履约状态以权益中心 / 履约任务为准 | 任何跨系统合并状态都会降低异常可见性 |
| 操作模式 | 高风险动作均二次确认并写审计；服务端最终鉴权和校验 | 若缺少审计，将无法满足财务和安全追溯 |

## 2. 信息架构、入口与用户流程

### 2.1 入口与路由

| 入口 | 前置条件 | 路由 / 页面 | 初始参数 | 返回 / 关闭后 |
|---|---|---|---|---|
| 侧边栏「订单管理 / 套餐订单」 | `package_order.read` | `/package-orders`；原型 `Prototype/套餐订单.html` | 默认全部状态、创建时间倒序 | 保留最近一次页面内筛选状态 |
| 异常通知深链 | 查看权限且订单存在 | `/package-orders?orderId={id}` | 自动打开目标订单详情 | 关闭详情后保留列表上下文 |
| 运营待办 | 查看权限 | `/package-orders?fulfillmentStatus=FAILED` | 预筛选履约失败 | 重置后回到默认列表 |

### 2.2 主流程

```text
进入套餐订单
 -> 鉴权并加载状态计数与列表
 -> 使用 Tab / 筛选定位订单
 -> 查看订单详情
 -> 根据服务端返回的 allowed_actions 展示操作
 -> 待支付：关闭订单
 -> 待履约 / 履约失败：补发或重试履约
 -> 已履约：发起退款
 -> 退款失败：重试退款
 -> 权益回收失败：重试回收
 -> 二次确认 / 填写原因
 -> 服务端鉴权、状态校验、幂等校验
 -> 同步返回受理结果
 -> 已受理：刷新状态，详情跟踪异步进度
 -> 状态冲突：刷新最新状态并提示
 -> 失败：保留上下文，允许恢复
```

### 2.3 支付后履约流程

```text
支付渠道成功回调
 -> 支付服务验签、金额和商户订单校验
 -> 订单支付状态置为 PAID（幂等）
 -> 创建履约任务（order_id + fulfillment_version 唯一）
 -> 读取下单时套餐快照
 -> 解析个人 / 企业权益归属主体
 -> 权益中心原子写入：权益项、环境数、成员席位、有效期
 -> 成功：FULFILLED，记录生效前后快照和完成时间
 -> 失败：FULFILL_FAILED，记录可读失败原因并进入告警 / 人工重试队列
```

### 2.4 退款与权益回收流程

```text
人工发起退款
 -> 权限、支付状态、退款金额和重复退款校验
 -> 权益中心预检可回收性
 -> 创建退款单，订单进入 REFUNDING
 -> 支付渠道原路退款
 -> 失败：REFUND_FAILED，可重试，不改变既有权益
 -> 成功：REFUNDED，触发权益回收任务
 -> 回收成功：REVOKED，流程闭环
 -> 回收失败：REVOKE_FAILED，P0 告警并允许重试回收
```

#### 3.0.1 整体布局

- 主内容区内边距 16px，业务卡片不使用外描边，采用 8px 圆角。
- 页面从上到下为：页面标题与刷新时间 -> 状态 Tab -> 筛选区 -> 列表工具栏 -> 表格 -> 分页。
- 详情使用右侧 800px 抽屉；关闭、履约、退款使用居中 Modal / Dialog；Toast 固定顶部居中。
- 768-1279px 保留系统壳层；筛选项自然换行；仅表格容器横向滚动。

### 3.1 状态 Tab

| Tab | 过滤规则 | 说明 |
|---|---|---|
| 全部 | 不附加状态 | 默认 |
| 待支付 | `payment_status=PENDING` | 包含未超时订单 |
| 待履约 | `payment_status=PAID AND fulfillment_status=PENDING` | 支付成功但任务尚未开始 |
| 履约中 | `fulfillment_status=PROCESSING` | 包含人工重试任务 |
| 已履约 | `fulfillment_status=FULFILLED` 且未进入退款 | 权益已确认到账 |
| 退款中 | `refund_status=PROCESSING` | 不允许重复发起 |
| 已退款 | `refund_status=SUCCESS` | 详情继续展示权益回收结果 |
| 已关闭 | `payment_status=CLOSED` | 终态，只读 |

### 3.4 操作规则

| 操作 | 可用前置状态 | 弹窗字段 | 成功响应 | 失败 / 冲突 |

| 查看详情 | 任意 | 无 | 打开详情抽屉 | 订单不存在则提示并刷新列表 |
| 关闭订单 | 待支付 | 关闭原因（必填，预设原因 + 备注最多 200 字） | 变为已关闭 | 已支付则拒绝并刷新 |

### 3.6 空、加载、错误与权限状态

- 首次加载：表头保留，表体展示 8 行骨架屏。
- 默认无数据：展示「暂无套餐订单」。
- 筛选无结果：展示「未找到匹配订单」和「重置筛选」。
- 局部错误：展示「订单列表加载失败」和「重新加载」，筛选值不丢失。
- 页面无权限：展示明确无权限状态；不请求业务列表。
- 操作无权限：入口隐藏；服务端仍必须鉴权并可返回权限错误。

## 4. 权限、可见性与数据安全

### 4.1 权限矩阵

| 权限码 | 能力 | 运营 | 客服 | 财务 | 管理员 | 审计 |
|---|---|---:|---:|---:|---:|---:|
| `package_order.read` | 查看列表和详情 | 是 | 是 | 是 | 是 | 是 |
| `package_order.close` | 关闭待支付订单 | 否 | 是 | 否 | 是 | 否 |
| `package_order.fulfill_retry` | 补发 / 重试履约 | 否 | 是 | 否 | 是 | 否 |
| `package_order.refund_create` | 发起退款 | 否 | 否 | 是 | 是 | 否 |
| `package_order.refund_retry` | 重试退款 | 否 | 否 | 是 | 是 | 否 |
| `package_order.revoke_retry` | 重试权益回收 | 否 | 否 | 否 | 是 | 否 |
| `package_order.audit_read` | 查看完整操作审计 | 否 | 部分 | 部分 | 是 | 是 |

### 4.2 数据安全

- 页面权限、操作权限和数据范围均由服务端判定；前端隐藏按钮不是安全边界。
- 手机号、邮箱、支付流水号默认脱敏；列表不提供明文展示。
- 不在 URL、埋点和前端日志中记录手机号、邮箱、完整支付流水、退款原因原文。
- 高风险操作记录操作者 ID、角色、订单版本、前后状态、原因、请求 ID、IP 摘要和结果。
- 退款原因与操作日志的保留期由财务 / 合规评审确定；在确认前不得自行删除。

## 5. 数据模型、业务规则与状态机

### 5.1 领域对象

| 对象 | 核心字段 | 说明 |
|---|---|---|
| PackageOrder | order_id、subject_type、subject_id、order_type、amount、payment_status、version | 套餐订单聚合根 |
| PackageSnapshot | package_id、package_name、package_version、benefits、environment_limit、seat_limit、duration | 下单时不可变快照 |
| PaymentRecord | payment_id、channel、paid_amount、paid_at、status、transaction_masked | 支付事实 |
| FulfillmentTask | task_id、order_id、version、status、attempt_count、error_summary | 权益授予 / 回收异步任务 |
| EntitlementChange | subject_id、before_snapshot、after_snapshot、effective_at、expire_at | 权益变更审计 |
| RefundOrder | refund_id、order_id、amount、reason_code、status、channel_result | 退款事实 |
| OperationLog | operator、action、reason、before_status、after_status、request_id、created_at | 人工操作审计 |

### 5.2 枚举与状态机

**支付 / 订单状态 SM-01：**

```text
PENDING（待支付） -> PAID（已支付）
PENDING（待支付） -> CLOSED（已关闭）
PAID（已支付） -> REFUNDING（退款中） -> REFUNDED（已退款）
 -> REFUND_FAILED（退款失败） -> REFUNDING
```

**履约状态 SM-02：**

```text
NOT_APPLICABLE（未支付）
PAID -> PENDING（待履约） -> PROCESSING（履约中） -> FULFILLED（已履约）
 -> FULFILL_FAILED（履约失败） -> PROCESSING
REFUNDED -> REVOKING（回收中） -> REVOKED（已回收）
 -> REVOKE_FAILED（回收失败） -> REVOKING
```

禁止转换：已关闭不得直接变为已支付；已退款不得再次退款；履约中不得并行创建第二个有效履约任务；未支付不得履约。

### 5.3 业务规则

| 编号 | 规则 |
|---|---|
| BR-01 | 套餐订单必须保存下单时套餐快照，历史订单不得随套餐配置更新而改变。 |
| BR-02 | 个人和企业权益写入不同主体空间，`subject_type + subject_id` 必须与订单一致。 |
| BR-03 | 支付回调须校验签名、商户订单号、币种和金额；校验成功后才可置为已支付。 |
| BR-04 | 每个订单和履约版本最多存在一个有效履约结果；重试复用业务幂等键。 |
| BR-05 | 环境数、成员席位和有效期由套餐快照授予；后台不可手工编辑。 |
| BR-06 | 新购从履约成功时生效；续费在未到期时从原到期日顺延，已到期则从履约成功时生效。 |
| BR-07 | 订单操作入口以服务端 `allowed_actions` 为准，前端本地状态仅用于展示。 |
| BR-08 | 一期退款金额固定为订单可退全额，操作人不可编辑金额。 |
| BR-09 | 退款前必须完成权益可回收预检；预检失败时不得发起渠道退款。 |
| BR-10 | 渠道退款成功但权益回收失败时资金事实不可回滚；须 P0 告警并人工重试回收。 |
| BR-11 | 所有高风险操作必须填写原因、二次确认并记录审计。 |
| BR-12 | 状态计数与列表查询使用同一筛选口径，允许存在可说明的秒级异步延迟。 |

### 5.4 并发、幂等与一致性

- 列表 / 详情返回 `version`；关闭、履约和退款请求携带该版本。版本不一致返回 `ORDER_STATE_CHANGED`。
- 履约幂等键：`FULFILL:{order_id}:{fulfillment_version}`；回收幂等键：`REVOKE:{refund_id}`。
- 退款幂等键由客户端请求 ID 与订单 ID 组成，服务端创建唯一退款单。
- 支付状态、履约状态采用最终一致；详情时间线展示各系统已确认事件，不伪造统一事务。
- 使用事务消息 / Outbox 确保订单状态更新与履约任务创建至少一次投递；消费者必须幂等。

## 6. 接口与前后端契约

### 6.1 接口清单

| 编号 | 方法与路径 | 用途 | 关键入参 | 关键出参 |
|---|---|---|---|---|
| API-01 | `GET /admin/package-orders` | 列表查询 | page、page_size、filters、tab | items、total、status_counts |
| API-02 | `GET /admin/package-orders/{id}` | 详情 | order_id | order、snapshot、payment、fulfillment、timeline、allowed_actions |
| API-03 | `GET /admin/packages/options` | 套餐筛选选项 | subject_type（可选） | package_id、name、enabled |
| API-04 | `POST /admin/package-orders/{id}/close` | 关闭订单 | version、reason_code、remark、request_id | latest_order |
| API-05 | `POST /admin/package-orders/{id}/fulfillment/retry` | 补发 / 重试履约 | version、request_id | task_id、status |
| API-06 | `POST /admin/package-orders/{id}/refunds` | 发起退款 | version、reason_code、remark、request_id | refund_id、status |
| API-07 | `POST /admin/package-orders/{id}/refunds/{refundId}/retry` | 重试退款 | version、request_id | refund_id、status |
| API-08 | `POST /admin/package-orders/{id}/revocation/retry` | 重试权益回收 | version、request_id | task_id、status |

### 6.2 通用响应与错误

```json
{
 "code": "OK",
 "message": "success",
 "request_id": "req_20260813_xxx",
 "data": {}
}
```

| 错误码 | 前端处理 |
|---|---|
| `ORDER_NOT_FOUND` | 关闭抽屉并刷新列表，提示订单不存在 |
| `ORDER_STATE_CHANGED` | T-03，刷新详情和当前行 |
| `ACTION_NOT_ALLOWED` | 展示服务端可读原因，刷新 allowed_actions |
| `ENTITLEMENT_NOT_REVOKABLE` | 退款弹窗内展示不可回收原因，不提交退款 |
| `DUPLICATE_REQUEST` | 查询原任务 / 退款单状态，不重复创建 |
| `PAYMENT_CHANNEL_UNAVAILABLE` | 保留退款失败态，展示 T-07 |
| `FORBIDDEN` | T-09；移除无权操作入口 |

### 6.3 异步任务

- 履约、退款和权益回收均可异步执行；提交成功只表示任务已受理，不表示业务终态成功。
- 详情打开时每 5 秒轮询进行中任务；抽屉关闭或页面不可见时停止轮询。
- 任务终态后刷新订单详情、列表当前行和 Tab 计数。
- 任务超过 5 分钟仍处理中触发告警；前端展示「处理中，请稍后刷新」，不自动判失败。

## 7. 异常、边界与降级

| 场景 | 页面表现 | 数据处理 | 恢复方式 |
|---|---|---|---|
| 列表接口失败 | 内容区错误态，不覆盖筛选 | 保留上次已确认数据（若有） | 重新加载 |
| 详情接口失败 | 抽屉内错误提示 | 列表不变 | 重试详情 |
| 支付系统不可用 | 展示已确认支付状态和同步时间 | 禁止凭前端推断更新 | 稍后刷新 / 告警 |
| 权益中心不可用 | 履约 / 回收任务失败或处理中 | 不重复授予 / 回收 | 幂等重试 |
| 退款通道不可用 | 退款失败 | 原权益不变 | 财务重试退款 |
| 页面离线 | Toast 网络异常 | 不提前修改状态 | 网络恢复后重新查询 |
| 无权限 | 无权限态 / 隐藏操作 | 不请求敏感数据 | 联系管理员授权 |

## 8. 配置、埋点、日志与监控

### 8.1 可运营配置

- 支付有效期、异步超时阈值、重试次数和告警接收人由服务端配置中心管理。
- 前端不得硬编码退款资格和 allowed_actions。
- 套餐筛选选项来自套餐中心，历史下架套餐仍可在订单结果中展示。

### 8.2 埋点事件

| 事件名 | 触发时机 | 关键属性（不含敏感原文） |
|---|---|---|
| `package_order_page_view` | 页面首屏成功展示 | role、entry |
| `package_order_filter_submit` | 提交筛选 | subject_type、order_type、status、has_keyword |
| `package_order_detail_view` | 详情打开成功 | order_type、subject_type、payment_status、fulfillment_status |
| `package_order_action_submit` | 高风险操作提交 | action、before_status、role |
| `package_order_action_result` | 操作同步受理结果 | action、result、error_category |

### 8.3 审计与告警

| 编号 | 监控 / 告警 |

## 11. 发布、灰度与回滚

- 先只读灰度：上线列表、详情和审计，核对支付 / 履约状态准确性。
- 再按角色灰度关闭和履约重试；退款最后开放给白名单财务账号。
- 每个操作能力由服务端 Feature Flag 独立控制；关闭 Flag 后页面只读，不影响订单查询。
- 若状态映射异常，回滚操作入口并保留只读查询；不得回滚已确认的支付、履约或退款事实。
- 上线前完成支付订单、履约记录和权益快照抽样对账。
